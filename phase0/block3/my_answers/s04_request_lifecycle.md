# S4: PHP のリクエストモデルを理解する

## 1. PHP の「リクエストごとプロセスモデル」とは何ですか?Java の常駐プロセス型と比較して、図解で説明してください。

プロセスが1リクエストごとに、起動 → 処理 → 終了 をするモデル。
Javaでは、常駐型のプロセスモデルを採用しており、1つのプロセスが起動し続けている。

---
### PHP: リクエストごとプロセス型

ブラウザから1リクエスト来るたびに、PHPプロセスが**ゼロから立ち上がって・処理して・終わる**というモデルです。Apacheの`mod_php`にしろ`PHP-FPM`にしろ、基本の考え方は同じです。

つまりこういう流れになります。

1. リクエストが届く
2. PHPプロセスがスクリプトを読み込んで実行する
3. レスポンスを返す
4. プロセスのメモリが**すべて破棄される**
5. 次のリクエストはまたゼロから

`$counter = 0;` と書いて`$counter++` しても、リクエストが終われば消えます。次のリクエストでは、また `$counter = 0` から始まります。だからセッションやDB、ファイルなど「外部の入れ物」に状態を保存する必要があるんですね。

### Java: 常駐プロセス型 (JVM)

Java(SpringやTomcatなど)は、**JVMというプロセスが1つずっと起動し続けている**モデルです。

1. サーバー起動時にJVMが立ち上がる(1回だけ)
2. クラスをロードして、DBコネクションプールも準備して、メモリ上に**常駐**
3. リクエストが来たら、JVM内で**スレッド**を割り当てて処理
4. 処理が終わってもJVMは生きたまま
5. 次のリクエストは、起動済みのJVMが**待ち構えた状態**で受ける

`static`なカウンタを `counter++` すれば、その値はJVMが動いている限り**残り続けます**。

### 普段触っているところで言うと

Laravelで`config/database.php`を読んだり、ルーティングを解決したり、サービスコンテナを組み立てたり…という処理が、**理論上は毎リクエストごとに走っている**ということです(実際は OPcacheで多少緩和されてはいますが)。これがJava(Spring Boot等)では、起動時に1回だけ済ませて、あとはずっと使い回します。

### この違いから生まれる実務上のクセ

| 観点 | PHP | Java |
|---|---|---|
| 状態の保持 | 外部(DB, Redis, セッション)に出す | アプリ内メモリでも保持できる |
| 起動コスト | 毎リクエスト発生(でも軽い) | 初回のみ(でも重い) |
| 並行処理の罠 | ほぼ気にしなくていい | スレッドセーフを常に意識 |
| メモリリーク | 起きてもすぐ消える | 蓄積して落ちる原因になる |
| デプロイ | ファイル置き換えで反映 | プロセス再起動が必要 |

PHPが「**書きやすくて壊れにくい**」と言われるのは、毎回プロセスが死んでくれるおかげで、変な状態がたまらないからです。一方、Javaが「**高速で大規模向き**」と言われるのは、JVMが温まった後は起動コストなしで処理できるし、メモリ上のキャッシュやコネクションプールをフル活用できるからですね。

## 2. なぜ PHP では、グローバル変数や静的変数が次のリクエストに引き継がれないのですか?

正確には引き継がれているが、1リクエストを処理する間しかプロセスが生きていないだけ。

---

### 答えの核心: 「グローバル」と「静的」の意味を取り違えやすい

実は、PHPの`global`変数や`static`変数は、**ちゃんと「次の処理」には引き継がれています**。引き継がれていないのではなく、**「次の処理」の範囲が思っているより狭い**だけなんです。

| 修飾子 | 寿命の範囲 |
|---|---|
| ローカル変数 | その関数が終わるまで |
| `global` 変数 | **そのプロセスが生きている間** |
| `static` 変数 | **そのプロセスが生きている間** |

つまり`global`も`static`も「プロセスが生きている間」が上限です。Javaだと「JVMが生きている間 = サーバーが動いている間」だから、実質ずっと残ります。PHPは「1リクエスト処理する間」しかプロセスが生きていないので、結果として**1リクエスト分しか生きない**わけです。

### なぜプロセスが違うとメモリが見えないのか

これはPHPの仕様というより、**OSレベルの大原則**です。

OSは各プロセスに「**仮想メモリ空間**」という独立した世界を割り当てます。プロセスAが`0x7f00...`というアドレスを指しても、プロセスBの`0x7f00...`はまったく別の物理メモリを指します。これはセキュリティ上めちゃくちゃ重要で、もしこれが許されていたら、隣のWebサイトのプロセスからクレジットカード情報を読み放題になってしまいます。

`static`変数は、コンパイラ/インタプリタが「このプロセスのメモリ空間内の固定位置に確保してね」と指示するだけのもの。**プロセスが終われば、その「固定位置」ごと消えます**。

### Javaの`static`と何が違うのか

これは混乱しやすい点なので、Java Silverで`static`を学んだMaruさんは特に意識すると良いと思います。

```java
// Java: JVMが起動している限り残り続ける
public class Counter {
    public static int count = 0;
}
```

```php
// PHP: このリクエスト処理が終わるまでしか残らない
class Counter {
    public static int $count = 0;
}
```

**書き方はそっくりなのに、寿命が天と地ほど違う**。これはJava経験者がPHPに来たときによく踏む落とし穴です。

### だからPHPでは「外」に状態を出す

「リクエスト間で値を保持したい」と思ったら、**プロセスより長生きする場所**に書き出すしかありません。

- **セッション** (`$_SESSION`) — 内部的にはファイルやRedisに書いて、次回読み戻している
- **データベース** — プロセスが死んでもDBは生きている
- **キャッシュ** (Redis, Memcached) — 専用の常駐プロセスが持っている
- **ファイル** — ディスクに書く
- **APCu / OPcache** — Webサーバープロセスが持つ共有メモリ(やや特殊)

Laravelで`session(['key' => 'value'])`や`Cache::put()`をよく見ると思いますが、これらは全部「**プロセスの外に状態を逃がす仕組み**」です。なぜそんな仕組みが必要なのか、今回の話で腑に落ちると思います。

逆に言うと、Javaの世界では`@Component`でDIされたシングルトンの`Service`クラスがメモリ上に居続けるので、そこにキャッシュを持たせる…なんてこともできるわけですね。同じWebアプリでも、設計の発想が結構違うのはこのへんが効いています。

## 3. PHP がリクエストごとにプロセスを立ち上げて捨てるなら、なぜそれでも実用的な Web アプリケーションが作れるのですか?(= セッション、DB、キャッシュの役割)

状態を外部に保存しているため。
セッション＝誰か、DB＝アプリ本体データ、キャッシュ＝セッションを保存。

--- 
これは本質を突いた良い問いです。「毎回ゼロからやり直し」なら、ユーザーのログイン状態も買い物カゴも保てないはずですよね。でも実際にPHPで巨大なWebアプリ(WordPress、Wikipedia、Slack初期版、Facebook初期版など)が動いている。その秘密を図解しますね。## 発想の転換: 「アプリ自身が覚える」をやめる

PHPの実用性の秘密は、考え方をひっくり返したところにあります。

Javaの感覚だと、「アプリケーション自身が情報を覚えている」のが自然です。`static`なフィールドや、DIされたシングルトンの`Service`が、メモリ上に状態を抱えている。

PHPはこれを潔く諦めて、**「自分は何も覚えない。覚える役は外の専門家に任せる」**という分業体制をとっています。PHPプロセスは、毎回**「短期記憶喪失の優秀な職人」**のように振る舞うんですね。職人自身は前回のお客さんを覚えていないけれど、カウンターの帳簿(DB)を見れば、誰が何を注文したかすぐにわかる。

## 役割分担を整理すると

### セッション: 「このユーザーは誰か」を覚える係

ブラウザは、ログイン後に発行された**セッションID**をCookieに入れて毎リクエスト送ってきます。PHPはこのIDをキーにして、保存先(デフォルトはサーバー上のファイル、Laravelだと`storage/framework/sessions/`)から該当ユーザーの情報を読み戻します。

```php
// PHPプロセスは「自分は誰を相手にしているか」を知らない
session_start();  // ← CookieのセッションIDを使って外部から読み込む
echo $_SESSION['user_name'];  // 「ああ、Maruさんでしたね」
```

職人がカウンター下の帳簿を開いて「ああ、Maruさんでしたね」と思い出す瞬間です。

### データベース: 「アプリの本体データ」を覚える係

ユーザー、投稿、注文、商品 — つまり**消えてはいけないデータ**は全部ここに置きます。MySQLやPostgreSQLは**別プロセス**として24時間動いていて、PHPプロセスが何回死のうがお構いなしに生き続けます。

PHPプロセスが起動するたびに新しい接続を作るとコストが高いので、`PHP-FPM`なら接続を使い回したり、`Persistent Connection`を使ったりします(LaravelだとEloquentがよしなにやってくれる)。

### キャッシュ (Redis等): 「高速アクセス」と「セッションの保存先」係

DBに毎回問い合わせると遅いので、よく使うデータはRedisに置いておきます。Redisも**メモリ上に常駐するプロセス**なので、PHPからは「外の倉庫」として使えます。

実は、本番のLaravelアプリではセッション自体もRedisに置くことが多いです。ファイルだと複数のWebサーバーで状態を共有できないけど、Redisならどのサーバーからでも同じセッションを読めるので。

## 「合言葉」の存在が全てを成立させている

ここで一番大事なポイントを強調しておきます。

**ブラウザがセッションIDというCookieを毎回送ってくるおかげで、PHPは記憶喪失のままでも「あなたが誰か」を思い出せる**んです。

Cookieがなかったら、PHPは毎回完全な他人としてユーザーに接することになり、ログインなんて不可能でした。**HTTPがステートレスなプロトコルなのに、Cookieという小さな仕組み一つでステートフルなアプリが作れる** — これはWeb全体のすごく大事な発明で、PHPはそれを最大限活用しているわけですね。

## Javaとの設計思想の違い

| 観点 | PHP | Java (Spring等) |
|---|---|---|
| 状態を持つ主体 | **外部ストレージ** | **アプリ本体 + 外部ストレージ** |
| 起動コスト | 毎回(でも軽い) | 1回だけ(でも重い) |
| メモリキャッシュ | 苦手 (やるならRedis) | 得意 (`@Cacheable`等) |
| スケールアウト | **しやすい** | やや工夫が必要 |
| シンプルさ | 短く書ける | 設計が必要 |

実は、**PHPの「何も覚えない」設計はスケールアウトとの相性が抜群**です。Webサーバーを10台に増やしても、どのサーバーがリクエストを受けても結果は同じ(状態は全部外部にあるので)。これがWordPressやMediaWikiが世界中で大規模運用されている理由の一つです。

Javaの場合、メモリ上に状態を持てる便利さの裏返しで、「このリクエストはどのサーバーが処理するか」を意識する必要が出てきます(スティッキーセッション、分散キャッシュ等)。

## Maruさんが今後Laravelで触るところ

今後Phase 2あたりで触ることになる以下の機能は、全部この「外に状態を逃がす」発想で動いています。

- `session(['key' => $value])` — セッションへの書き込み
- `Cache::remember()` — Redis等への一時保存
- `Auth::user()` — セッションから現在のユーザーを復元
- `Cookie::queue()` — Cookieにデータを乗せる
- Eloquent全般 — DBが「アプリの記憶装置」

「**プロセスが死んでも困らないように、覚えておくべきものは外に書き出す**」という意識を持って読むと、なぜこれらの機能が必要なのか、すんなり腑に落ちると思いますよ。

## 4. Laravel は内部的にどうやって、リクエスト間で状態を保っていますか?

毎回、外部から状態を読み込んで、メモリ上に再構築する作業を行っている

---
これは前回の話を一段具体化する、すごく良い問いです。「外に状態を逃がす」と言われても、Laravelの中でそれが**どう実装されているか**が見えないと、なんとなく魔法に感じてしまいますよね。Laravelの内部を覗いてみましょう。## 答え: Laravel自体は「状態を保つ」ことを諦めている

身も蓋もない答えですが、これが真実です。**Laravelフレームワーク本体は、リクエスト間で何一つ覚えていません**。毎回、上の図の①から⑦を全部やり直しています。

ではなぜ「状態が保たれているように見える」のかというと、Laravelがやっているのは「**毎回、外部から状態を読み込んで、メモリ上に再構築する作業**」だからです。例えるなら、**毎朝オフィスに出社して、書類キャビネット(DB)から関連ファイルを取り出して机に並べ直す**ようなもの。机の上は毎晩リセットされるけど、キャビネットの中身は無事、というわけです。

## 鍵を握る2つの仕組み

### 1. サービスコンテナ(`Application`クラス)

`public/index.php`を覗くと、こんなコードがあります。

```php
$app = require_once __DIR__.'/../bootstrap/app.php';
$kernel = $app->make(Kernel::class);
$response = $kernel->handle($request);
```

この`$app`が**サービスコンテナ**で、Laravelのほぼ全機能(DB、認証、キャッシュ、ルーティング…)はこの中に登録されます。重要なのは、**`$app`はリクエストごとに新規生成される**ということ。前回のリクエストの`$app`はもうこの世にいません。

`Auth::user()`や`DB::table()`のような**ファサード**は、内部的にはこの`$app`コンテナから対応するオブジェクトを取り出しているだけです。

```php
// Auth::user() の内部はざっくりこんなイメージ
$app['auth']->guard()->user();
//      ↑ コンテナから AuthManager を取り出している
```

### 2. ServiceProvider(「設計図」の登録)

`config/app.php`に並んでいる`providers`配列。これがLaravelの起動シーケンスで一番大事な部分です。

```php
'providers' => [
    Illuminate\Auth\AuthServiceProvider::class,
    Illuminate\Database\DatabaseServiceProvider::class,
    Illuminate\Session\SessionServiceProvider::class,
    // ...
],
```

各ProviderはLaravel起動時に呼ばれ、コンテナに「こういうサービスが欲しいと言われたら、こう作って渡してね」という**設計図(バインディング)**を登録します。

```php
// SessionServiceProvider の中身を簡略化したもの
public function register() {
    $this->app->singleton('session', function ($app) {
        return new SessionManager($app);  // 必要になった時に作られる
    });
}
```

つまり、③のbootstrapで毎回**「Laravelとはこういうフレームワークである」という設計図を組み立て直している**わけです。プロセスは死んでも、コード(設計図)はディスクに残っているので、毎回同じLaravelが再現される、というカラクリです。

## 「リクエスト間の状態」が具体的にどう持ち回されるか

それぞれの機能で、状態の保存先が違います。Maruさんが普段Laravelで触っているものを並べてみますね。

| 機能 | 保存先 | キー(合言葉) |
|---|---|---|
| `Auth::user()` | DB (`users`テーブル) | セッション内の`login_web_xxx` という`user_id` |
| `session(['key' => $v])` | `storage/framework/sessions/` か Redis | Cookieの`laravel_session` |
| `Cache::put('k', $v)` | Redis / Memcached / DB / ファイル | キャッシュキー文字列 |
| `Cookie::queue(...)` | ブラウザ | Cookie名 |
| Eloquentモデル | DB | 主キー |

つまり**全部、外のどこかに置かれていて、何らかのキーで取り出している**だけなんです。

## ③のbootstrap、毎回やってて重くないの?

これがMaruさんが既に知っている**OPcache**の出番です。

PHPはデフォルトだと、リクエストのたびにPHPファイルを読み込んで構文解析し、バイトコードに変換します。LaravelのbootstrapはServiceProviderを何十個も登録するので、これを毎回やったら確かに遅い。

OPcacheは**バイトコード(構文解析した結果)を共有メモリにキャッシュ**してくれます。だから2回目以降のリクエストでは、ディスクからの読み込みも構文解析もスキップできます。

さらにLaravelは`php artisan config:cache`や`route:cache`で、設定やルート定義を**1つのファイルにまとめて事前生成**する機能を提供しています。本番環境ではこれを使うと、bootstrap時間が大幅に短縮されます。

```bash
# 本番デプロイ時によく走らせるやつ
php artisan config:cache    # 設定ファイル群を1つに
php artisan route:cache     # ルート定義をコンパイル
php artisan view:cache      # Bladeテンプレートを事前コンパイル
```

ただし**実体オブジェクト(DB接続、SessionManagerのインスタンスなど)は依然として毎回作り直し**です。キャッシュされるのはあくまでコード/設定の解析結果まで。

## Maruさんの会社のコードで確認するなら

実際のLaravelプロジェクトで、この流れを目で追ってみると一気に腑に落ちると思います。おすすめの順番は以下です。

1. **`public/index.php`** — 全ての始まり、20行くらいしかない
2. **`bootstrap/app.php`** — `Application`が生成される場所
3. **`config/app.php`** の `providers` 配列 — 何が登録されているかの一覧
4. **`app/Http/Kernel.php`** の `$middleware` と `$middlewareGroups` — リクエストが通る経路
5. **`vendor/laravel/framework/src/Illuminate/Session/Middleware/StartSession.php`** — セッションが復元される実装の本体

Phase 2の「Laravel実践」フェーズで、ぜひこの流れをデバッガで一歩ずつ追ってみてください。「**フレームワークが何をやってくれていて、自分は何を書いているのか**」の境界線が見えると、Laravelが急に透明な存在になります。これが見えるか見えないかで、その後の理解度がだいぶ変わりますよ。
