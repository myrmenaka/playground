# S4 解説: PHP のリクエストモデル

## このStepのポイント

PHP は Java と **根本的に異なる動作モデル** を持っている。これを「Shared-Nothing アーキテクチャ」または「リクエストごとプロセスモデル」と呼ぶ。

## PHP のリクエストモデル

### 1リクエストの流れ

```
[クライアント] --HTTP--> [Webサーバ(Apache/Nginx)]
                            ↓
                     PHPプロセスを起動
                            ↓
                  ① PHPファイルを読み込み・コンパイル
                  ② コードを実行(変数・オブジェクトはメモリ上)
                  ③ レスポンスを返す
                  ④ プロセスを終了(メモリは全部解放)
                            ↓
                  [次のリクエスト] -- 最初からやり直し
```

重要なのは ④。**リクエストが終わると、すべての変数・オブジェクト・接続は破棄される**。
次のリクエストは、完全にゼロからスタートする。

つまり、PHP のプロセスは **何も共有しない (Shared-Nothing)**。

### Java(Tomcat など)との対比

```
Java の動き方:
  サーバ起動 → JVM 起動 → アプリケーションをメモリにロード
                                    ↓
  リクエスト1 → 既存のJVMで処理 → レスポンス(状態はメモリに残る)
  リクエスト2 → 既存のJVMで処理 → レスポンス(状態はメモリに残る)
  リクエスト3 → 既存のJVMで処理 → レスポンス
                                    ↓
                              サーバ停止まで動き続ける

PHP の動き方:
  リクエスト1 → プロセス起動 → 処理 → レスポンス → プロセス終了(全部消える)
  リクエスト2 → プロセス起動 → 処理 → レスポンス → プロセス終了(全部消える)
  リクエスト3 → プロセス起動 → 処理 → レスポンス → プロセス終了(全部消える)
```

| 項目 | Java(Tomcat 等) | PHP |
|------|---------------------|-----|
| プロセスのライフサイクル | 常駐(サーバ停止まで) | リクエストごとに起動・終了 |
| 静的変数の寿命 | サーバ停止まで保持 | リクエスト終了で消える |
| シングルトン | 全リクエストで共有 | リクエスト内のみ |
| メモリ管理 | GCで継続的に管理 | リクエスト終了で全解放 |
| 起動コスト | サーバ起動時に1回 | リクエストごと(最近は最適化あり) |

### このモデルのメリット・デメリット

**メリット**

- **メモリリークの心配が薄い**: リクエスト終了で全解放されるので、書いた人がうっかりリークを作っても被害が1リクエスト内に収まる
- **デプロイが楽**: ファイルを置き換えるだけで反映される(再起動不要)
- **障害の影響が局所的**: 1つのリクエストでクラッシュしても、他のリクエストに影響しない
- **学習コストが低い**: 「グローバル状態を管理する」という概念が無いので、最初は単純に書ける

**デメリット**

- **起動コストが毎回かかる**: フレームワークの初期化、設定読み込みなどがリクエストごとに発生
- **状態を持てない**: メモリ上で何かを覚えておくことができないので、必ず外部(DB、Redis、ファイル)に保存が必要
- **永続的なコネクションが持てない**: DB 接続もリクエストごとに作り直し(コネクションプールで緩和されてはいる)

### 最近の状況: OPcache と Swoole

純粋なリクエストごとプロセスモデルは起動コストが高い。これを改善する仕組みもある:

- **OPcache**: コンパイル結果をメモリにキャッシュ。コード自体の解析コストを削減(これは現代の標準)
- **Swoole / RoadRunner / FrankenPHP**: PHP を常駐プロセスとして動かす拡張。Java に近い動作モデルを実現できるが、Shared-Nothing 前提のコードと相性問題あり

業務で目にするのは主に OPcache。Swoole 系は最近徐々に増えているが、まだ少数派。

## なぜセッションや DB が「必要」か

PHP のリクエストモデルから、必然的に以下が要求される:

### 状態を「外」に持つ必要がある

リクエスト間で何かを覚えておきたい(ログイン状態、カート内容、ユーザー設定など)場合、メモリでは不可能。必ず外部に保存が必要。

| 保存先 | 用途 | 寿命 |
|--------|------|------|
| Cookie | クライアント側に保存。セッションIDなど | 設定次第 |
| セッション | サーバ側のファイルや DB に保存。ユーザー固有データ | ログアウトまで |
| データベース | 永続データ。ユーザー情報、投稿、注文など | 永続 |
| Redis / Memcached | 高速アクセスが必要な揮発データ。キャッシュ、ジョブキュー | 設定次第 |

Java なら、ある程度の状態は JVM のメモリで持てる(シングルトン、Application スコープなど)。
PHP では、**どんな小さな状態でも外部に置く必要がある**。これは欠点ではなく、PHP の特性。

### 「ステートレス」が前提

このモデルにより、PHP アプリケーションは **本質的にステートレス** になる。

これは現代のクラウド環境(Kubernetes、オートスケール、ロードバランサ)とは相性が良い。
複数のサーバに同じアプリケーションを並べて、リクエストをどこに振っても結果が同じになるからだ。

Java アプリケーションでセッションをメモリに持つと、「同じユーザーは同じサーバに振り分ける(セッションスティッキー)」が必要になり、スケーラビリティの足かせになる。
PHP は最初からこの問題がない。

## Laravel ではどう扱っているか(Phase 1 への布石)

Laravel は、PHP のリクエストモデルの上に **状態を持っているように見せる仕組み** を構築している:

- **セッション**: `session()->put('cart', $items)` のように書ける。裏では、毎リクエストでセッションIDを Cookie から取得 → ストレージから状態を読み込み → リクエスト終了時に保存、をやっている
- **認証**: ログイン状態はセッションに保存。`Auth::user()` は毎リクエストで DB からユーザーを読み直している(キャッシュあり)
- **設定**: `config('app.name')` のように使うが、これも毎リクエストで `config/` ディレクトリの PHP ファイルを読み込んでいる(本番では `php artisan config:cache` で1ファイルにまとめてキャッシュする)
- **サービスコンテナ**: アプリケーションのオブジェクト管理。**リクエスト内では** シングルトンに見えるが、**リクエストを跨ぐと別物**

Phase 1 でこれらに出会った時、「リクエスト間で状態をどう保っているか」を意識して読むと、Laravel の設計の妙が見えてくる。

## Java エンジニアが特に間違えやすいポイント

### 1. 「static 変数で値を保持できる」と思ってしまう

```php
class Counter {
    public static int $count = 0;
}

Counter::$count++;
// このリクエスト内ではインクリメントされるが、
// 次のリクエストでは $count は 0 に戻っている
```

Java なら静的変数はサーバ起動中ずっと保持される。PHP では「リクエスト内のグローバル変数」程度の意味しか持たない。

### 2. 「シングルトンで状態を持てる」と思ってしまう

```php
class Cache {
    private static ?self $instance = null;
    private array $data = [];

    public static function getInstance(): self {
        if (self::$instance === null) {
            self::$instance = new self();
        }
        return self::$instance;
    }
}

Cache::getInstance()->set('key', 'value');
// 次のリクエストでは、$data は空に戻っている
```

シングルトンも「リクエスト内で1つ」を保証するだけで、リクエスト間では別物。
キャッシュとして使うなら Redis などの外部ストレージが必要。

### 3. 「DB 接続をリクエスト間で使い回したい」と思ってしまう

PHP では各リクエストで DB 接続を作り直すのが基本。
パフォーマンス問題があれば、PDO の永続接続(`PDO::ATTR_PERSISTENT`)や、PHP-FPM のコネクションプールで対処する。

## ノートアプリへのメモ推奨内容

```
## PHP のリクエストモデル

- リクエストごとにプロセスを起動 → コード実行 → プロセス終了
- リクエスト終了でメモリは全部解放される
- 「Shared-Nothing アーキテクチャ」と呼ばれる

## Java との違い

- Java(Tomcat): JVM が常駐。状態はメモリに残せる
- PHP: 毎リクエスト起動・終了。状態は外部に置く必要

## 必然的に必要になるもの

- セッション: ユーザー単位の状態を覚えておくため
- DB: 永続データ、リクエスト間共有データ
- キャッシュ(Redis等): 高速アクセスが必要な揮発データ

## Java エンジニアの落とし穴

- 静的変数で状態を保持しようとする → リクエスト終了で消える
- シングルトンで状態を持とうとする → リクエスト内のみ有効
- 「メモリにキャッシュ」は使えない → 外部キャッシュサーバが必要

## メリット

- メモリリークの被害が局所的
- 本質的にステートレス → クラウド・スケールアウトと相性良し
- デプロイが楽(再起動不要)
```
