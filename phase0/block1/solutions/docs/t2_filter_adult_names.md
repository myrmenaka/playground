# T2 解説: 成人ユーザーの名前を抽出する関数

## ポイント

### 連想配列の配列の扱い

このテストの核心は「**2階層のデータ構造**」を扱えるか。

```php
[
    ['name' => 'Alice', 'age' => 25],   // 1要素 = ユーザー1人(連想配列)
    ['name' => 'Bob',   'age' => 17],
    // ...
]
```

外側の配列 = ユーザーのリスト、内側の連想配列 = ユーザー1人の情報。
ループの中で扱う `$user` は「**ユーザー1人分の連想配列**」となるので、`$user['name']` や `$user['age']` でフィールドにアクセスできる。

これは Laravel の Eloquent モデルや API レスポンスでも頻出する構造。**「リスト → 個別オブジェクト → フィールド」の3階層**で考える癖をつけたい。

---

### ※「リスト → 個別オブジェクト → フィールド」とは

T2 で扱った構造を、もう一度よく見てみてください。

```php
$users = [
    ['name' => 'Alice', 'age' => 25],   // ← 個別オブジェクト
    ['name' => 'Bob',   'age' => 17],
    ['name' => 'Charlie', 'age' => 30],
];
```

ここには **3つの階層** があります。

| 階層 | 何を表すか | T2 のコードでの形 |
|------|----------|------------------|
| **リスト** | 複数の要素の集まり | `$users`(配列全体) |
| **個別オブジェクト** | 1つの要素 | `$user`(連想配列1個) |
| **フィールド** | オブジェクトの属性 | `$user['name']`, `$user['age']` |

T2 のループ処理を見ると、この3階層を順に降りていることが分かります。

```php
foreach ($users as $user) {       // リスト → 個別オブジェクト
    $user['name']                 // 個別オブジェクト → フィールド
}
```

### ■ なぜ「3階層で考える癖」が大事なのか

実務で複雑なデータを扱うとき、**頭の中で「今どの階層にいるか」を意識できるかどうか**で、コードが書けるかが決まります。

### ■ よくある混乱パターン

たとえば、新人さんがよくやってしまうミスがこちらです。

```php
foreach ($users as $user) {
    if ($users['age'] >= 20) {     // ❌ $users(リスト)のキー 'age' を見ている
        $result[] = $user['name'];
    }
}
```

`$users` と `$user` を取り違えています。**「今扱っているのはリストなのか、個別オブジェクトなのか」を見失っている**状態です。3階層を意識していれば、「ループの中では `$user`(個別オブジェクト)を扱う」と即座に判断できます。

### ■ もう一つよくある混乱

```php
$result = [];
foreach ($users as $user) {
    $result[] = $user;            // ❌ ユーザー全体を入れてしまう
}
// 期待: ['Alice', 'Charlie', 'Eve']
// 実際: [['name'=>'Alice', 'age'=>25], ['name'=>'Charlie', ...], ...]
```

これも「**個別オブジェクト**を入れたいのか、その中の**フィールド**を入れたいのか」が混乱した結果です。3階層を意識していれば、「フィールドを抜き出すなら `$user['name']` まで降りる」と判断できます。

### ■ 階層が4階層、5階層になることもある

実務では、もっと深い階層を扱うこともあります。

#### 例: ユーザーごとに複数の投稿を持つ構造

```php
$users = [
    [
        'name' => 'Alice',
        'posts' => [
            ['title' => 'Hello',  'views' => 100],
            ['title' => 'PHP入門', 'views' => 250],
        ],
    ],
    [
        'name' => 'Bob',
        'posts' => [
            ['title' => 'Laravel楽しい', 'views' => 500],
        ],
    ],
];
```

これは **4階層** の構造です:

| 階層 | 例 |
|------|-----|
| リスト | `$users` |
| 個別オブジェクト(ユーザー) | `$user` |
| フィールド(投稿リスト) | `$user['posts']` |
| 個別オブジェクト(投稿) | `$post` |
| フィールド(タイトル等) | `$post['title']` |

これを処理するときは **ループの中にループ**(ネスト)が入ります:

```php
foreach ($users as $user) {                    // 階層1 → 階層2
    foreach ($user['posts'] as $post) {        // 階層3 → 階層4
        echo $user['name'] . ' / ' . $post['title'] . PHP_EOL;
    }
}
```

各階層で「今何を扱っているか」を見失わないことが、コードを書く上での核心スキルになります。

### ■ まとめ

「リスト → 個別オブジェクト → フィールド」の3階層を意識する癖をつけると、次のような場面で詰まりにくくなります。

1. **データベースのレコード一覧の処理**(Eloquent)
2. **API レスポンスの処理**(JSON のパース後)
3. **フォーム送信データの処理**(複数項目)
4. **ファイル読み込み結果の処理**(CSV など)

実務のコードのほとんどは、この構造の組み合わせで書かれている、と言っても言い過ぎではありません。今は連想配列で扱っていますが、Phase 2 で Eloquent モデルが登場すると、**「個別オブジェクト」がクラスのインスタンスになる**だけで、考え方は完全に同じです。

T2 で **`$users` → `$user` → `$user['name']`** と段階的に降りていく書き方ができていたのは、この感覚がすでに育っている証拠です。Block 2 でクラスを学んだあとに、改めてこの考え方を振り返ると、より腑に落ちると思います。

### 境界値の扱い(超重要)

```
「20歳以上」 → age >= 20 → 20を含む
「20歳超」   → age > 20  → 20を含まない
「20歳以下」 → age <= 20 → 20を含む
「20歳未満」 → age < 20  → 20を含まない
```

要件を1文字ずつ正確に読み、対応する演算子を選ぶ。実務で最も多いバグの1つが「以上/以下/超/未満」の取り違え。**テストを書く前から境界値を意識する**癖をつけたい。

### 「フィルター」と「変換」の組み合わせ

このテストは S19 のフィルターをさらに発展させた処理。

| 処理 | 内容 |
|------|------|
| **フィルター** | 条件を満たすユーザーだけ残す(20歳以上) |
| **変換**(マップ) | 残ったユーザーから `name` だけを取り出す |

これは関数型プログラミングでいう **filter + map** の典型パターン。今回は1つの `foreach` で両方を同時にやっている。

## 別解

### 早期 continue 版

```php
function filterAdultNames(array $users): array
{
    $result = [];
    foreach ($users as $user) {
        if ($user['age'] < 20) {
            continue;   // 未成年はスキップ
        }
        $result[] = $user['name'];
    }
    return $result;
}
```

模範解答(if で条件を満たすケース)と早期 continue 版、どちらも正解。**処理が複雑になるほど早期 continue 版のほうが読みやすくなる**。

### 組み込み関数の組み合わせ

```php
function filterAdultNames(array $users): array
{
    $adults = array_filter($users, fn($user) => $user['age'] >= 20);
    return array_values(array_map(fn($user) => $user['name'], $adults));
}
```

`array_filter` でフィルター、`array_map` で変換、`array_values` でキー振り直し。1行で書けるが、`foreach` 版より読みにくい場面もある。実務では Laravel の Collection で書くことが多い。

### Laravel Collection で書くと(参考)

```php
function filterAdultNames(array $users): array
{
    return collect($users)
        ->filter(fn($user) => $user['age'] >= 20)
        ->pluck('name')          // 連想配列から特定キーだけ抜き出す
        ->values()
        ->toArray();
}
```

`pluck('name')` という Laravel 独自のメソッドが超便利。「名前だけ抜き出す」という意図が一目で分かる。Phase 2 で詳しく扱う。

## つまずきやすい点

### 1. 境界値の判定ミス

```php
if ($user['age'] <= 20)   // ❌ 「20歳以下」をスキップ → 20歳が消える
if ($user['age'] < 20)    // ⭕ 「20歳未満」をスキップ → 20歳が残る
if ($user['age'] >= 20)   // ⭕ 「20歳以上」を残す → 20歳が残る
```

「以上」を表現するなら **`>=`** を使うのが直感的。「未満をスキップ」と裏返して **`<`** を使う場合は、頭の中で論理を反転させる必要があるので、**書いた直後に境界値で動作確認**する癖をつけたい。

### 2. 連想配列のキーアクセスでクォートを忘れる

```php
$user['name']     // ⭕ 文字列キーはクォート必須
$user[name]       // ❌ 定数 name を探す → Notice
$user['name ']    // ❌ 末尾にスペース → 別のキーになる
```

PHP では文字列キーを必ずクォートで囲む。クォートなしだと「定数名」と解釈されて Notice が出る。

### 3. キーが存在しないケースの考慮

```php
$user = ['name' => 'Alice'];   // age がない
$user['age']                    // Warning: Undefined array key
```

実務では入力データが期待通りでないことがある。安全に書くなら:

```php
$age = $user['age'] ?? 0;       // null合体演算子(PHP 7+)
$age = $user['age'] ?? null;    // null をデフォルトに
```

ただし学習段階では「入力は仕様通り」を前提にしてOK。Phase 2 以降のバリデーションや、Phase 3 のセキュリティ章で深掘りする。

### 4. `$result[] = $user;`(ユーザー丸ごと)と `$result[] = $user['name'];`(名前だけ)の取り違え

```php
$result[] = $user;            // ❌ ユーザーの連想配列を丸ごと入れてしまう
$result[] = $user['name'];    // ⭕ name の値だけを取り出す
```

問題文を最後まで読み、「**何を返すべきか**」を意識する。「名前だけ」を抽出する仕様なので、`$user['name']` を取り出してから追加する。

## Java との対比

```java
// Java(POJO + Stream)
class User {
    String name;
    int age;
    // ... コンストラクタ、getter
}

public static List<String> filterAdultNames(List<User> users) {
    return users.stream()
        .filter(u -> u.getAge() >= 20)
        .map(User::getName)
        .collect(Collectors.toList());
}
```

```php
// PHP(連想配列 + foreach)
function filterAdultNames(array $users): array
{
    $result = [];
    foreach ($users as $user) {
        if ($user['age'] >= 20) {
            $result[] = $user['name'];
        }
    }
    return $result;
}
```

| 観点 | Java | PHP |
|------|------|-----|
| データ構造 | クラス(`User`)で型を定義 | 連想配列(型なし) |
| フィールドアクセス | `user.getAge()` または `user.age` | `$user['age']` |
| Stream の filter + map | `.filter().map().collect()` | `foreach` の中で両方 |
| 型の安全性 | コンパイル時にチェック | 実行時にエラー、またはノーチェック |

Java の最大の利点は「**`User` クラスとして型を定義できる**」こと。これにより `user.getAge()` が補完で出てきて、間違ったフィールド名(例: `getAg()`)はコンパイル時に検出される。

PHP の連想配列は手軽だが、`$user['age']` のキー名は文字列なのでタイポがあっても実行時まで分からない。これを補うのが Laravel の **Eloquent モデル** や **DTO クラス** の利用で、Phase 2 以降で扱う。

実務での重要ポイント:
- **連想配列で書くのは「軽い処理」「一時的なデータ」まで**
- **永続化するデータや、複数箇所で扱うデータはクラス化する**
- **API レスポンスは連想配列で受け取り、内部で扱う時はクラス/モデルに変換**

これらは Phase 2(Eloquent)、Phase 4(設計)、Phase 5(DDD)で深く学ぶ。今回の T2 で「連想配列で書くと型の保護がない」という弱点を体感できたのは、その先の学びへの大事な伏線になる。
