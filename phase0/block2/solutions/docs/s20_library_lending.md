# S20 解説: 分解して書く手順を身につける

## このStepの本当の目的

S20 はコードを書くこと自体は易しい。本当の目的は **「いきなり書き始めずに、分解してから書く」習慣を体に入れる** こと。

S19 で「クラスや役割が増えると俯瞰できなくなる」という気付きを得た。これは多くの新人が通る壁で、対策は1つ —— **頭の中で全部を同時に考えようとしないこと**。

人間の短期記憶はせいぜい4〜7個の項目しか同時に保持できない。S19 では「Product クラスの構造」「3種類の例外」「メソッドの引数」「動作確認の流れ」を全部頭で抱えようとして、容量オーバーになった。

解決策は単純で、**頭の外(コメントや紙)に書き出して、目で追えるようにする** こと。

## 5ステップの手順

| Step | 内容 | この段階で考えること |
|------|------|-----------------|
| 1 | 登場人物を洗い出す | クラスと例外の **名前** だけ |
| 2 | メソッド一覧表を作る | **シグネチャ**(名前・引数・戻り値)だけ、中身は考えない |
| 3 | 骨組みを空のまま書く | **構造** だけ、ロジックは書かない |
| 4 | メソッド中身を1つずつ | **そのメソッド1つ** だけに集中 |
| 5 | 動作確認コードを書く | **正常系 → 異常系** の順 |

各 Step で **考えることを意図的に制限している** のがポイント。Step 1 の時点では「borrow メソッドの中身どうしよう」は考えない。Step 4 で borrow を書く時は「他のメソッドどうしよう」は考えない。

## なぜ Step 1〜2 を「コメント」として残すのか

書き終わった後にコメントを消しても動く。なのに残す理由は2つ:

1. **読み手への設計意図の伝達**: 後でファイルを開いた人(将来の自分を含む)が、上から読むだけで「このファイルには何があるか」を5秒で把握できる
2. **書き手の思考の固定**: コメントを書く時点で頭の中の設計を文字に固定するので、Step 4 で迷子になりにくい

業務で複雑な機能を書く時も、コメントで設計を先に書く人は **手戻りが少ない**。これは「コーディング前に紙に書く」の現代版。

## 動作確認の書き方:try-catch の使い分け

これは S20 のもう1つの隠れた論点。

### 良くない例

```php
try {
    $book->borrow();  // 成功する前提
    echo "貸し出しました" . PHP_EOL;
} catch (BookAlreadyBorrowedException $e) {
    echo "エラー: {$e->getMessage()}" . PHP_EOL;
}
```

これでも **動く**。しかし読み手に「ここで例外が出る可能性があるのか?」と一瞬迷わせる。

### 良い例

```php
$book->borrow();  // 成功する前提 → try-catch 不要
echo "貸し出しました" . PHP_EOL;

try {
    $book->borrow();  // 失敗する前提
} catch (BookAlreadyBorrowedException $e) {
    echo "エラー: {$e->getMessage()}" . PHP_EOL;
}
```

**コードの形を見ただけで意図が読める**。try-catch は「ここで例外が出る前提」という視覚的なマーカーになっている。

### 業務での判断基準

業務のアプリケーションコードでは、判断基準が少し変わる。

| 状況 | try-catch する? |
|------|---------------|
| そのメソッド固有の対応がある(例: 在庫不足 → 在庫補充を提案) | する |
| 上位の例外ハンドラーに任せて良い | しない |

Laravel には `app/Exceptions/Handler.php` という例外ハンドラーがあり、コントローラで catch しなかった例外は自動的にそこで処理される。**「囲まない勇気」のほうが大事** という場面が多い。

## 細かい書き方の話

### `=== true` / `=== false` は省略するのが慣習

```php
// 冗長
if ($this->borrowed === true) { ... }
if ($this->borrowed === false) { ... }

// 慣習版
if ($this->borrowed) { ... }
if (!$this->borrowed) { ... }
```

`private bool $borrowed` のように **型宣言済みの bool** なら、`"0"` などの罠は発生しない。`=== true` は冗長。

ただし `?bool`(nullable bool)の場合は要注意:

```php
private ?bool $borrowed = null;  // null / true / false の3状態

if ($this->borrowed === false) { /* false の時だけ */ }
if (!$this->borrowed) { /* false でも null でも通る ← 意味が違う */ }
```

Java で言うと `boolean`(プリミティブ、null なし)と `Boolean`(参照型、null あり)の違い。

### ダブルクォーテーション内の式展開

PHP の文字列展開には制約がある:

| 書き方 | 展開できる? |
|--------|-----------|
| `"$variable"` | ◯ 単純な変数 |
| `"{$variable}"` | ◯ 変数(中括弧付き) |
| `"{$obj->prop}"` | ◯ プロパティアクセス |
| `"{$obj->method()}"` | ◯ メソッド呼び出し |
| `"{$arr['key']}"` | ◯ 配列要素 |
| `"{$a + $b}"` | ✗ 演算は不可 |
| `"{$cond ? 'a' : 'b'}"` | ✗ 三項演算子は不可 |
| `"{strlen($s)}"` | ✗ 関数呼び出しは不可 |

「変数や式の **アクセス** は展開できるが、**評価結果** は展開できない」と覚える。
パーサーが文字列内では限定的な構文しか解釈しないため。

#### 回避策

```php
// 案1: 一時変数(最も読みやすい、業務でよく使われる)
$status = $book->isBorrowed() ? 'はい' : 'いいえ';
echo "貸し出し中: {$status}" . PHP_EOL;

// 案2: 文字列連結
echo "貸し出し中: " . ($book->isBorrowed() ? 'はい' : 'いいえ') . PHP_EOL;

// 案3: sprintf
echo sprintf("貸し出し中: %s", $book->isBorrowed() ? 'はい' : 'いいえ') . PHP_EOL;
```

長くなる式は案1(一時変数)が最も可読性が高い。

## Java との対比

| 項目 | Java | PHP |
|------|------|-----|
| カスタム例外 | `class XException extends Exception` | `class XException extends \Exception` |
| 例外のスロー | `throw new XException(msg)` | `throw new XException(msg)` |
| 文字列フォーマット | `String.format("%s", x)` | `"$x"` or `"{$x}"` |
| bool 比較 | `if (x)` が慣習 | `if ($x)` が慣習(型宣言ありなら) |
| nullable | `Boolean`(参照型) | `?bool`(union 型) |

PHP の文字列展開は Java にはない便利な機能。ただし「式の評価結果」は展開できない制約がある。

## つまずきやすい点

1. **「とりあえず書き始める」誘惑**
   特に簡単に見える題材だと、Step 1〜3 をすっ飛ばしたくなる。**簡単な題材で手順を踏む** ことに価値がある。手順が体に入っていれば、難しい題材でも同じ手順で対応できる。

2. **「全部 try-catch で囲む」癖**
   最初は安全に倒したくて、すべて try-catch で囲みがち。しかし **「例外が飛ぶ場所」を視覚的に明示する** のが本来の使い方。

3. **`=== true` のような過剰な防御**
   PHP の `==` の罠を知っているからこその防御だが、型宣言済みの bool なら不要。慣習に従う方が読み手の認知負荷が下がる。
