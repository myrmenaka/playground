# S17 解説: インターフェースと抽象クラスの違いを整理する時のポイント

このStepは「自分の言葉でメモを書く」ことが目的のため、模範解答のメモは置かない。
ここでは指導側(メンター)が押さえておくべきポイントをまとめる。
学習者が「うまくメモが書けない」と感じた時の参照資料としても使える。

---

## 学習者がつまずきやすい4つの壁

### 壁1: 「結局どっち使えばいいの?」

S17 段階で最も多い質問。
S11〜S16 を通じてコードレベルでは違いを体感しているが、設計判断としての使い分けはまだ難しい。

伝え方:
> 「迷ったら『能力(can do)を表したい → インターフェース』『分類(is-a)で共通実装を持たせたい → 抽象クラス』で判断してOK。Phase 2 で Laravel の `Authenticatable` `Notifiable` などを見ると体感が深まります」

### 壁2: 「抽象クラスのメリットが分からない」

S15〜S16 では子クラスが `Dog` 1つだけなので、抽象クラスの旨味を実感しづらい。
「複数の子クラスで共通処理を1か所にまとめられる」という価値は、子クラスが2つ以上ある場面で初めて腹落ちする。

伝え方:
> 「`Dog` だけだと旨味が見えにくいですが、`Cat` や `Bird` を足すと、親の `introduce()` がそのまま使い回せることが価値になります。Block 2 完了テストの後で実感が来るはずです」

### 壁3: プロパティを持てるかの混同

学習者が間違いやすいポイント TOP1。
- インターフェース: プロパティ持てない(**定数のみOK**)
- 抽象クラス: プロパティ持てる

「契約書には『どんな状態を持つか』は書かない、書くのは『どんな振る舞いをするか』だけ」という比喩で説明すると腑に落ちやすい。

### 壁4: 「Java と違う点」

| 観点 | Java | PHP |
|------|------|-----|
| デフォルトメソッド | Java 8+ で可能 | **不可**(抽象クラスで代用) |
| `@Override` | あり | なし(`#[\Override]` 属性は PHP 8.3+) |
| `abstract public` の語順 | `public abstract` | `abstract public`(逆) |
| プロパティの `final` | あり | `readonly`(PHP 8.1+)で類似 |
| record / data class | Java 14+ | コンストラクタプロモーションで代用 |

## 模範メモの例(レベル別)

学習者が「自分のメモが浅い気がする」と言った時に提示できる、3段階の到達点。

### レベル1: S17 時点のゴール(これが書ければOK)

```
インターフェース: 「○○できる」という能力(契約)を表す。
                  メソッドの形だけ決めて、実装は各クラスに任せる。

抽象クラス: 「○○の一種である」という分類を表す。
            共通の処理は親に書き、違う部分だけ子に任せる。
```

### レベル2: Block 2 完了時のゴール

```
インターフェース: 異なるクラスに「同じ振る舞いを持っている」ことを保証する仕組み。
                  呼ぶ側は具体的なクラスを知らなくても、インターフェース型として扱える。
                  多重実装ができるので「複数の能力を組み合わせる」のに向く。

抽象クラス: 共通の状態(プロパティ)と共通の処理(具体メソッド)を親に持たせつつ、
            子クラスごとに変えたい部分だけ抽象メソッドとして任せる仕組み。
            単一継承なので「分類の階層」を表現するのに向く。
```

### レベル3: Phase 4(リファクタリング)以降のゴール

```
インターフェース: 実装を切り替え可能にする仕掛け。
                  テスト時のモック差し替え、依存性逆転(DIP)、
                  Strategy パターン、Repository パターンなどの基盤。
                  「外から見える型」と「中の実装」を分離するための道具。

抽象クラス: テンプレートメソッドパターンの直接的な実装手段。
            「処理の骨格は決まっているが、一部のステップは状況によって変える」
            という場合に使う。フレームワークの基底クラス設計でよく登場。
```

S17 ではレベル1〜2 で十分。レベル3 は Phase 4(設計・リファクタリング)で自然に到達する。

## 文法上の違いの完全版(レビュー時の確認用)

| 観点 | インターフェース | 抽象クラス |
|------|----------------|----------|
| キーワード | `interface` | `abstract class` |
| プロパティを持てるか | **持てない**(定数のみOK) | 持てる |
| コンストラクタを持てるか | 持てない | 持てる |
| メソッドの実装を持てるか | 持てない(宣言のみ) | 持てる(抽象と具体を混在可) |
| 多重実装/継承 | 多重実装できる(`implements A, B`) | 単一継承のみ(`extends` は1つ) |
| インスタンス化 | できない | できない |
| メソッドの可視性 | `public` のみ | `public` / `protected` / `private` 全部可 |
| 定数 | 持てる | 持てる |
| 静的メソッド | 宣言できる | 宣言できる(具体・抽象両方) |

## 使い分けの判断基準(実務観点)

学習者が「使い分けが言語化できない」と言ったら、以下の判断軸を提示するとよい。

### インターフェースを選ぶ時

- 「これは○○できる」という **能力** を表現したい
- 異なる継承階層のクラスに **同じ能力** を持たせたい
- **複数の能力** を組み合わせたい(多重実装)
- 実装の詳細を隠して **契約だけ** 表に出したい

実例:
- Laravel の `Authenticatable`(認証できる)
- Laravel の `Arrayable`(配列に変換できる)
- 自作の `Searchable`(検索できる)
- 自作の `Cacheable`(キャッシュできる)

### 抽象クラスを選ぶ時

- 「これは○○の一種である」という **分類** を表現したい
- 子クラス間で **共通のプロパティ・処理** を持たせたい(コピペを避けたい)
- 処理の **骨格は決めて、一部だけ子に任せたい**(テンプレートメソッド)
- 共通の **コンストラクタロジック** を持たせたい

実例:
- Laravel の `Illuminate\Database\Eloquent\Model`(全モデルの基底)
- Laravel の `Illuminate\Routing\Controller`(全コントローラの基底)
- 自作の `AbstractRepository`(共通のCRUD処理を持つリポジトリ基底)

### 「両方使う」が現実解

実務では片方だけ使うのではなく、**両方組み合わせる** ことが多い。
例えば Laravel の `Model` は抽象クラスっぽい役割を持ちつつ、各モデルは `Authenticatable` などのインターフェースも `implements` する。

学習者がここまで腹落ちするのは Phase 2 〜 3 になってから。S17 段階では「使い分けの考え方がある」と知るだけで十分。
