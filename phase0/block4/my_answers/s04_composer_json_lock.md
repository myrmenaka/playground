- `composer.json` は誰が書く?何を宣言している?
    - 開発者が手で書くファイル（実際にはほとんどのケースでComposerコマンド経由で書かれる）
    - 「このプロジェクトが何に依存しているか」を **人間の意図として宣言** するもの
    - 「設計書・要望書」
    - 「依存パッケージ」→ プロジェクトが動くために必要なライブラリと、そのバージョン範囲
    - 「オートロード設定」→ **このネームスペースは、このディレクトリにマッピングする** という宣言
    - 「メタ情報・スクリプト」→ パッケージ名、ライセンス、スクリプト（独自コマンド）など
一言でいうと：買い物リスト（～以上の糖度の苺が欲しい）

- `composer.lock` はいつ生成・更新される?何を記録している?
    - composer.lock は composer install（lockが無い時）・composer update・composer require / remove を実行したタイミングで生成・更新される
    - Composerが自動生成するもので、基本的に人間が手で編集してはいけない
    - 記録しているのは「依存解決の結果、実際にインストールされた全パッケージの正確なバージョンとハッシュ」
    - composer install は「lock に書いてある通りに入れる」。lock があればそれを最優先し、composer.json に新しい要望が増えていても無視する（厳密には不整合があると警告/エラー）
    - composer update は「composer.json の範囲内で最新を取り直して、lock を書き換える」
    - composer.lock には、解決された全パッケージについて以下が記録される
        1. 正確なバージョン：実際にインストールされたバージョン（ピン留めされた一点）
        2. 取得元とハッシュ：パッケージ配布元URL、参照、配布物のshasumなど → これらにより、「同じ中身であること」を検証できる
        3. content-hash：composer.json の内容から計算したハッシュ、これが食い違った場合Composerが警告を出す
        4. その他のメタ情報：何由来のパッケージか（packages と packages-dev で分かれて記録）、安定性設定、プラットフォーム要件（PHPバージョンや拡張）など

| コマンド | composer.lock への影響 |  
|:--:|:--:|  
| composer install（lockが無い時） | composer.json を解決して 新規生成 |  
| composer install（lockが有る時） | 更新しない。lock の内容をそのまま再現するだけ |  
| composer update | 依存を解決し直して 更新（lock を書き換える） |  
| composer require <pkg> | パッケージ追加 → composer.json と lock を 更新 |  
| composer remove <pkg> | パッケージ削除 → 同じく両方を 更新 |  

一言でいうと：実際に買ってきたレシート（この苺は〇月〇日に正確に糖度〇という状態で購入した）

- `composer install` と `composer update` の動作はどう違うか

|  | composer install | composer update |  
|:--:|:--:|:--:|  
| 主に見るファイル | composer.lock | composer.json |  
| やること | lock に書かれた正確なバージョンを入れる | json の範囲で解決し直す |  
| lock の扱い | 読むだけ（書き換えない） | 書き換える |  
| 入るバージョン | 全員・全環境で同一 | 実行した時点の最新（範囲内） |  
| 典型的な使用場面 | 本番デプロイ、CI、チーム参加時 | ライブラリを上げたい時 |  

一言でいうと：install は「lock 通りに再現する」→ 既存の確定状態を忠実に再現、update は「lock を書き換える」→ composer.json の範囲内でバージョンを取り直して lock を更新

- なぜ2ファイルに分かれているのか(チーム開発・本番で何を保証するか)
    - composer.json は意図を、composer.lock は再現性を担当
    - チーム開発では「私の環境では動く」問題を消すのが最大の役割
    - 本番では「テストした個体」と「本番で動く個体」の同一性を保証
    - 開発・ステージング・本番という複数の環境を、依存に関して同じ状態でデプロイできること。手元で update してテストを通したら、その結果の lock をコミットし、各環境では install だけを打つ。すると：

ステージングで検証した依存 = 本番で動く依存（完全一致）
デプロイ時に依存が勝手に上がって本番だけ壊れる事故が起きない

※ 怖いのが、本番デプロイで誤って update を打つこと。手元では動いていたのに、デプロイ時に依存が勝手に上がって本番だけ壊れる、という事故が起きる。これを防ぐため、CI・本番では install のみ（しかも --no-dev などを付ける）が鉄則になっている

※ 「本番では install のみ」という鉄則は、まさにこの保証を守るための運用。lock があっても本番で update を打ってしまえば、この同一性は崩れる。2ファイル構造は仕組みを用意しただけで、それを守るのは運用だという点は押さえておく

※ 逆に「セキュリティ修正が出たから依存を上げたい」ときは、ローカルで update を打ち、生成された新しい lock をコミットしてレビュー → install で各環境に展開、という流れになる。update する人と場所を限定し、その結果を lock 経由で配るのがチーム運用の型

結論：2つに分けているのは、「人間の意図（柔らかい要望）」と「機械が確定した結果（硬い事実）」を分離するため

- `composer.lock` は Git にコミットすべきか

composer.lock を Git にコミットして共有すると、全員が composer install でlock に固定された同一バージョンを引く。新メンバーが参加しても、install 一発でチーム全員と同じカゴの中身が手に入る。これがチーム開発での保証となる

- まとめ

ここまでの「買い物リスト／レシート」を最終形にすると、

    - composer.json（リスト） = 「鮮度◯◯以上のトマトが欲しい」というあなたの基準。柔らかく、人が書き換える。
    - composer.lock（レシート） = 「2026年6月3日に、この産地・このロットのトマトを正確に買った」という確定記録。硬く、機械が発行する。

リストだけを渡されたら、人によって違うトマトを買ってくる。レシートまで渡すからこそ、誰がいつ買い直しても同じトマトが揃う。この「リストの柔らかさ」と「レシートの硬さ」を両立させるために、ファイルを2つに分けている——というのが全体の答え
