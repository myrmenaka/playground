# S4 解説: composer.json と composer.lock の違い

## 結論

- **`composer.json`** = 「どのパッケージが欲しいか(範囲指定の要求書)」
- **`composer.lock`** = 「実際に何のバージョンを入れたか(確定した記録)」

## キーポイント

### composer.json — 要求書

- 開発者が手で書く・編集するファイル
- 「欲しいパッケージ」と「許容するバージョン範囲」を宣言する
  - 例: `"monolog/monolog": "^3.0"` → 3.x 系なら最新でOK、という緩い指定
- いわばプロジェクトの「仕様」

### composer.lock — 確定記録

- `composer require` / `install` / `update` の時に自動生成・更新される(手では編集しない)
- 実際にインストールされた**正確なバージョン**を記録(例: `3.x.y` のようにピンポイント)
- 直接書いていない**間接依存(依存の依存)も全部**記録される
- 整合性チェック用のハッシュも持つ

### なぜ2つ必要か(本質)

`composer install` は `composer.lock` があれば、それに**完全に従って**インストールする。
これにより、チーム全員・CI・本番環境で**寸分違わず同じバージョン**が入る。
「自分の環境では動くのに本番で壊れる」を防ぐ仕組み。

| コマンド | 動作 |
|----------|------|
| `composer install` | lock 通りに入れる(lock 優先・再現性重視) |
| `composer update` | json の範囲で最新を解決し直し、lock を更新する |

## つまずきやすい点(よくあるミス)

- **`composer.lock` は Git にコミットする**(アプリ開発の場合)。`.gitignore` に入れてしまうと再現性が崩れる。
  - 補足: ライブラリ(他人に使わせるパッケージ)を作る側では lock をコミットしないのが通例。今は「アプリ側=コミットする」で覚えればOK。
- `install` と `update` の混同に注意。意図せず `update` すると lock が書き換わり、入るバージョンが変わってしまう。
- 「lock を消せば直る」と安易に削除しない。再現性の担保が失われる。

## 確認方法

S3 で `monolog/monolog` を入れた時、`composer.json` には範囲指定が、`composer.lock` には確定バージョンが書かれている。
両ファイルを開いて見比べると一発で腹落ちする。
